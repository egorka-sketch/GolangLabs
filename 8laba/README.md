# Лабораторная работа 8 — REST API пользователей

REST API на Go для управления пользователями: CRUD-операции, хранение в PostgreSQL,
валидация входных данных, централизованная обработка ошибок, пагинация и фильтрация.

**Стек:** Go 1.25 (стандартный `net/http`), PostgreSQL 18 в Docker, драйвер `pgx/v5`.

---

## Запуск

### 1. База данных

```bash
docker compose up -d
```

Поднимает PostgreSQL 18 на `localhost:5432` (пользователь `lab8`, пароль `lab8`, база `users`).
Данные хранятся в Docker-томе `pgdata` и переживают перезапуск контейнера.

### 2. Схема

Таблица создаётся один раз (например, через TablePlus или `psql`):

```sql
CREATE TABLE users (
    id        INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name      VARCHAR(30) NOT NULL,
    birth_day DATE NOT NULL
        CHECK (birth_day <= CURRENT_DATE AND birth_day >= '1900-01-01')
);
```

### 3. Сервер

```bash
go run ./cmd
```

Сервер слушает порт **8080**. Строка подключения к базе берётся из переменной окружения `DSN`;
если она не задана, используется значение по умолчанию:

```
postgres://lab8:lab8@localhost:5432/users?sslmode=disable
```

### 4. Тесты

```bash
go test ./... -v
```

Тесты хендлеров используют фейковый репозиторий, поэтому **база и Docker для них не нужны**.

## Модель данных

Пользователь в запросах и ответах:

| Поле        | Тип    | Описание                                          |
|-------------|--------|---------------------------------------------------|
| `id`        | число  | Идентификатор, генерируется базой. Только в ответах |
| `name`      | строка | Имя                                                |
| `birth_day` | строка | Дата рождения в формате `ГГГГ-ММ-ДД`               |

Пример:

```json
{"id": 1, "name": "Иван", "birth_day": "2001-03-15"}
```

### Правила валидации (`POST` и `PUT`)

| Поле        | Правило                                                         |
|-------------|-----------------------------------------------------------------|
| `name`      | обязательно; пробелы по краям обрезаются; не пустое после обрезки |
| `name`      | не длиннее 30 символов (считаются символы, а не байты)          |
| `birth_day` | обязательно; строго формат `ГГГГ-ММ-ДД`                          |
| `birth_day` | не в будущем                                                    |
| `birth_day` | не раньше `1900-01-01`                                           |

Те же ограничения продублированы в базе (`NOT NULL`, `VARCHAR(30)`, `CHECK`) как вторая линия защиты.

## Формат ошибок

Все ошибки возвращаются в едином виде:

```json
{"error": "текст ошибки"}
```

| Код | Когда                                                              |
|-----|--------------------------------------------------------------------|
| 400 | некорректный id, некорректный JSON, не пройдена валидация, неверные параметры запроса |
| 404 | пользователь с таким id не найден                                   |
| 405 | метод не поддерживается для этого пути (ответ формирует `ServeMux`)  |
| 500 | внутренняя ошибка сервера (подробности пишутся в лог, клиенту — общий текст) |

Решение о коде ответа принимается в одном месте — функции `handleError`.

## Маршруты

| Метод    | Путь          | Описание                          | Успех |
|----------|---------------|-----------------------------------|-------|
| `GET`    | `/users`      | список пользователей              | 200   |
| `GET`    | `/users/{id}` | один пользователь                 | 200   |
| `POST`   | `/users`      | создать пользователя              | 201   |
| `PUT`    | `/users/{id}` | обновить пользователя (полностью) | 200   |
| `DELETE` | `/users/{id}` | удалить пользователя              | 204   |

---

### `GET /users` — список пользователей

Возвращает массив пользователей, отсортированный по `id`. Пустой результат — `[]`.

**Параметры запроса** (все необязательные, комбинируются через «И»):

| Параметр  | Тип    | По умолчанию | Описание                                                    |
|-----------|--------|--------------|-------------------------------------------------------------|
| `limit`   | число  | 20           | размер страницы, от 1 до 100                                |
| `offset`  | число  | 0            | сколько записей пропустить, ≥ 0                             |
| `name`    | строка | —            | поиск по части имени без учёта регистра                     |
| `min_age` | число  | —            | возраст не меньше указанного (полных лет на сегодня), ≥ 0    |
| `max_age` | число  | —            | возраст не больше указанного, ≥ 0; не меньше `min_age`      |

Возраст в базе не хранится: фильтр переводится в условия на дату рождения
(`возраст ≥ N` ⇔ `birth_day ≤ сегодня − N лет`, `возраст ≤ N` ⇔ `birth_day > сегодня − (N+1) лет`).

**Ответы:** 200 — массив; 400 — неверный параметр; 500.

**Примеры:**

```bash
curl -s 'localhost:8080/users'
curl -s 'localhost:8080/users?limit=10&offset=20'
curl -s 'localhost:8080/users?name=ив'
curl -s 'localhost:8080/users?min_age=20&max_age=30'
curl -s 'localhost:8080/users?name=ив&min_age=20&limit=5'
```

```json
[
  {"id": 1, "name": "Иван", "birth_day": "2001-03-15"},
  {"id": 4, "name": "Ивлева", "birth_day": "2000-01-01"}
]
```

```bash
curl -s 'localhost:8080/users?limit=0'
# 400 {"error":"limit должен быть от 1 до 100"}

curl -s 'localhost:8080/users?min_age=30&max_age=20'
# 400 {"error":"min_age не может быть больше чем max_age"}
```

### `GET /users/{id}` — один пользователь

**Параметры пути:** `id` — целое число.

**Ответы:** 200 — пользователь; 400 — `id` не число; 404 — не найден; 500.

```bash
curl -i localhost:8080/users/1
```

```
HTTP/1.1 200 OK
Content-Type: application/json

{"id":1,"name":"Иван","birth_day":"2001-03-15"}
```

```bash
curl -s localhost:8080/users/999    # 404 {"error":"пользователь не найден"}
curl -s localhost:8080/users/abc    # 400 {"error":"некорректный id"}
```

---

### `POST /users` — создать пользователя

**Тело запроса:**

```json
{"name": "Иван", "birth_day": "2001-03-15"}
```

Поле `id` в теле не принимается — его назначает база.

**Ответы:** 201 — созданный пользователь с `id`; 400 — некорректный JSON или не пройдена валидация; 500.

```bash
curl -i -X POST localhost:8080/users -d '{"name":"Иван","birth_day":"2001-03-15"}'
```

```
HTTP/1.1 201 Created
Content-Type: application/json

{"id":5,"name":"Иван","birth_day":"2001-03-15"}
```

```bash
curl -s -X POST localhost:8080/users -d '{"name":"","birth_day":"2001-03-15"}'
# 400 {"error":"имя не может быть пустым"}

curl -s -X POST localhost:8080/users -d '{"name":"Иван","birth_day":"15.03.2001"}'
# 400 {"error":"дата рождения должна быть в формате ГГГГ-ММ-ДД"}

curl -s -X POST localhost:8080/users -d '{"name":"Иван","birth_day":"2030-01-01"}'
# 400 {"error":"дата не может быть в будущем"}
```

---

### `PUT /users/{id}` — обновить пользователя

Полная замена данных пользователя: в теле передаются **все** поля, как при создании.
`id` берётся только из пути; в теле его нет.

**Параметры пути:** `id` — целое число.
**Тело запроса:** как у `POST`.

**Ответы:** 200 — обновлённый пользователь; 400 — некорректный `id`, JSON или не пройдена валидация; 404 — не найден; 500.

```bash
curl -i -X PUT localhost:8080/users/1 -d '{"name":"Пётр","birth_day":"1999-07-01"}'
```

```
HTTP/1.1 200 OK
Content-Type: application/json

{"id":1,"name":"Пётр","birth_day":"1999-07-01"}
```

```bash
curl -s -X PUT localhost:8080/users/999 -d '{"name":"Пётр","birth_day":"1999-07-01"}'
# 404 {"error":"пользователь не найден"}
```

---

### `DELETE /users/{id}` — удалить пользователя

**Параметры пути:** `id` — целое число.

**Ответы:** 204 — удалён, тела нет; 400 — `id` не число; 404 — не найден; 500.

```bash
curl -i -X DELETE localhost:8080/users/1
```

```
HTTP/1.1 204 No Content
```

```bash
curl -s -X DELETE localhost:8080/users/999    # 404 {"error":"пользователь не найден"}
```

## Структура проекта

```
8laba/
├── cmd/
│   └── main.go              — точка входа: подключение к БД, маршруты, запуск сервера
├── internal/
│   ├── repository/
│   │   ├── user.go          — модель User, фильтр UserFilter, интерфейс UserRepository, ErrNotFound
│   │   └── postgres.go      — реализация репозитория на pgxpool, NewPool
│   └── handler/
│       ├── user.go          — HTTP-хендлеры, валидация, централизованная обработка ошибок
│       └── user_test.go     — unit-тесты всех маршрутов с фейковым репозиторием
├── docker-compose.yaml      — PostgreSQL 18
└── README.md
```

**Слои:**
- `handler` отвечает за HTTP: разбор запроса, валидацию, коды ответов, JSON.
- `repository` отвечает за SQL. Хендлеры зависят от интерфейса `UserRepository`,
  а не от конкретной реализации, поэтому в тестах её можно заменить фейком.
- Все SQL-запросы параметризованы (`$1`, `$2`, …) — значения клиента никогда
  не вклеиваются в текст запроса, что защищает от SQL-инъекций.
